### Build verification

**TypeScript typecheck:** `npx tsc --noEmit` → **PASS** (exit code 0, no errors).

**Native Android debug build:** `cd android && ./gradlew.bat assembleDebug` → **FAIL**

```
FAILURE: Build failed with an exception.
* Where:
Build file 'D:\iTantra\iTantra\android\build.gradle' line: 24
* What went wrong:
A problem occurred evaluating root project 'iTantra'.
> Failed to apply plugin 'com.facebook.react.rootproject'.
   > A problem occurred configuring project ':app'.
      > Failed to notify project evaluation listener.
         > The filename, directory name, or volume label syntax is incorrect
BUILD FAILED in 1m 15s
```

This fails during Gradle's **configuration phase** (before any Kotlin/Java compilation or native CMake build runs) — specifically while applying `com.facebook.react.rootproject` and notifying `:app`'s evaluation listener. "The filename, directory name, or volume label syntax is incorrect" is a Windows `CreateProcess` error (Win32 123), consistent with a malformed path being passed to a subprocess. `android/app/build.gradle`'s `react { }` block resolves `entryFile`, `reactNativeDir`, `hermesCommand`, and `codegenDir` via Groovy's `List.execute(envp, workingDir)` calls out to `node`, each of which is a plausible site for this class of failure on Windows — most commonly triggered by a space in a resolved path (e.g. `JAVA_HOME=C:\Program Files\Microsoft\jdk-17.0.12.7-hotspot` contains a space in "Program Files") interacting badly with how Gradle/Groovy quotes the subprocess command line. **This is a hypothesis, not a confirmed root cause** — it was not investigated further, because diagnosing/fixing the RN Gradle configuration is outside Phase 0's scope ("do not modify the existing RN implementation except for migration documentation").

**Evidence the app has built successfully in this environment before:** `android/app/build/outputs/apk/debug/app-debug.apk` exists on disk, dated **2026-09-05 00:13**, 104.75 MB, `applicationId: com.itantra.app`, `versionCode: 1`, `versionName: 1.0.0`, `minSdkVersionForDexing: 24` (per its `output-metadata.json`). This predates the current session and confirms the RN app is not fundamentally broken — something in the current invocation's environment (not necessarily the source tree, since `android/` is regenerated by `expo prebuild` and nothing under `src/` changed) currently prevents a fresh Gradle configuration pass from completing on this machine.

**This is recorded as a known issue, not fixed, per Phase 0 scope.** It does not block Phase 0 from being marked complete (Phase 0 is inspection + baseline-recording), but it **should be resolved or worked around before Phase 1 needs to build and install anything**, since Phase 1's exit criteria explicitly require installing a (new, Kotlin) APK on a physical device — a working Gradle/Android toolchain on this machine is a shared prerequisite for both the frozen RN baseline and the new Kotlin app.
