# iTantra — React Native → Native Android (Kotlin) Migration Audit

**Status: ANALYSIS ONLY. No code was migrated, rewritten, or modified to produce this document.**
Audit date: 2026-09-06. Source of truth: the actual files in this repository as of the commit at audit time (`dd40a64`), not prior descriptions of the project.

---

## A. EXECUTIVE SUMMARY

iTantra is a **React Native (Expo SDK 57) application**, not a native Android app today. The two Kotlin files that exist under `android/app/src/main/java/com/itantra/app/` (`MainActivity.kt`, `MainApplication.kt`) are **100% Expo/React Native boilerplate**, auto-generated by `expo prebuild` — the entire `android/` directory is git-ignored (`.gitignore:41`) and not a single file under it is tracked by git. There is currently **zero custom native Android code belonging to this project.**

The real product logic — VAD, sentence segmentation, STT routing, script repair, priority classification, packet construction, TTS queueing, and all UI — lives entirely in TypeScript under `src/`, running on the Hermes JS engine inside React Native's New Architecture (Fabric/TurboModules, `newArchEnabled: true`).

Speech inference itself is **not this project's code**. It is delegated to a third-party npm package, `react-native-sherpa-onnx@0.4.3` (author: XDcobra, MIT license), which is a React Native TurboModule wrapping prebuilt `sherpa-onnx` (k2-fsa) C++/ONNX Runtime binaries via JNI, plus bundled `ffmpeg` and `libarchive` prebuilt libraries for audio decoding and archive extraction. This is the component to **preserve, not rewrite**, in a Kotlin migration — either by depending on sherpa-onnx's own published Android AAR directly (bypassing the RN wrapper), or by lifting the wrapper's Kotlin/JNI glue code as a starting point.

The transport layer is **entirely mocked**. `MockTransport` loops a "sent" packet back to the same device's receive listeners after a randomized delay — there is no Bluetooth, Wi-Fi, LoRa, BLE, or socket code anywhere in the repository. The README and in-app text are explicit and honest about this ("THE TRANSPORT IS STILL A LOOPBACK").

All 10 languages are wired end-to-end (English via NeMo CTC, 9 Indic languages via AI4Bharat IndicConformer for STT; Piper for English/Hindi/Malayalam and Meta MMS for the other 7 for TTS), contingent on the corresponding model files being installed on-device (downloaded or side-loaded) — the STT/TTS pipeline runs the `SimulatedSttBackend` placeholder (which explicitly does not recognize speech) whenever a model is missing or the native module isn't present (e.g. Expo Go, web).

A migration to native Kotlin will remove the RN/Hermes/Fabric runtime overhead and the JS↔Native bridge, and gives cleaner access to `AudioRecord`/`AudioTrack`, foreground services, and lifecycle-correct coroutines — but it **cannot** speed up STT/TTS inference itself, because that already runs in native C++ ONNX Runtime today, off the JS thread. The performance case for migration is framework overhead and long-term maintainability, not raw model latency.

## B. CURRENT ARCHITECTURE

### Transmit path (voice → packet) — as actually implemented

```
Microphone (expo-audio useAudioStream, 16 kHz mono int16 request)
        │  onBuffer callback → raw ArrayBuffer + reported sampleRate
        ▼
AudioCaptureService (src/core/audio/AudioCaptureService.ts)
        │  int16→float32, resample to 16 kHz if hardware refused it,
        │  re-chop into exact 512-sample (32 ms) frames, carry remainder
        ▼
VadBackend  — EnergyVad (default) or SileroVad (opt-in, unused by default)
        │  per-frame speech probability, 0..1
        ▼
SentenceSegmenter (src/core/vad/SentenceSegmenter.ts)
        │  hysteresis state machine, pre-speech padding ring buffer,
        │  min-voiced-ratio gate (35%), pause flush (600/750/1000 ms),
        │  hard cap 15 s
        ▼
SttEngineProvider → SherpaSttBackend (react-native-sherpa-onnx TurboModule)
        │  falls back to SimulatedSttBackend if no native decoder/model
        ▼
indicScript.repairScript() — cross-script transliteration / rejection
hallucinations.isNonSpeechArtifact() — drops subtitle-artifact text
        ▼
packetFactory.buildPacket() → classifyPriority() keyword scan
        │  UUID v4 (expo-crypto), builds iTantraPacket
        ▼
Transport.sendPacket()  →  MockTransport (only implementation that exists)
```

### Receive path (packet → audio) — as actually implemented

```
Transport.onPacketReceived(packet)
        ▼
useReceiverController — dedup by packet.id, appends to history (cap 60)
        ▼
TtsManager.speakText(text, language, priority, packet.id)
        │  TtsQueue: CRITICAL jumps the queue and interrupts in-flight audio
        ▼
resolveTtsModelForLanguage() → TtsModelManager.resolvePath()
        ▼
TtsEngine.load() (react-native-sherpa-onnx TTS) → generateSpeech()
        │  saveAudioToFile() writes a WAV to app documents dir
        ▼
expo-audio createAudioPlayer(uri).play()  →  device speaker
```

Both controllers (`useTransmitterController`, `useReceiverController`) are instantiated once in `App.tsx` and share a single `MockTransport` instance — this is deliberate: `App.tsx`'s own comments explain that if either hook lived inside its screen component, switching modes would unmount it and lose the transport subscription (a bug that was previously hit and fixed).

## D. STT ARCHITECTURE

### Interfaces and implementations
- **`SttBackend`** interface (`src/core/stt/SttBackend.ts`): `kind`, `isReady`, `load(languageCode)`, `transcribe(samples, languageCode) → SttTranscription`, `dispose()`.
- **`SherpaSttBackend`**: the real decoder. Caches by `${modelId}:${sherpaLang}` key. Collapses concurrent `load()` calls from rapid language switching. Runs a dev-only self-test (`__DEV__` only) against a bundled reference clip on every load, logging raw tokens, repaired text, and decode time, to separate "the model is bad" from "the text-assembly is bad."
- **`SimulatedSttBackend`**: explicit non-recognizing placeholder. Reports segment duration and peak loudness; text is wrapped in brackets and impossible to mistake for a transcript. This is a **documented product decision**, not a stub to be casually replaced — an earlier version emitted realistic fake sentences and that was judged actively misleading.
- **`SttEngineProvider`**: chooses and owns the active backend. Order: try sherpa-onnx; on any failure, remember the language as unsupported (so it doesn't retry on every utterance) and fall back to simulated, loudly logging why. `reset()` clears that memory after a model install.

### Model manager
`ModelManager` (`src/core/stt/ModelManager.ts`) resolves an on-disk path per model id, checking a side-load directory (`<Documents>/itantra-models/<model-id>`) **before** the downloader — a hand-placed model always wins, which is the documented path for air-gapped demos. `install()` deliberately bypasses `react-native-sherpa-onnx`'s own model-registry lookup (documented bug: it fails to resolve a real asset sitting at a pagination boundary in a 498-asset GitHub release) and instead downloads directly from a stable release URL, or — for IndicConformer — fetches `tokens.txt` + `model.int8.onnx` as loose files from a specific Hugging Face repo per language.

### Preprocessing / audio contract
16 kHz mono, Float32 normalized to `[-1, 1]` (asymmetric int16 scaling: `/32768` for negative, `/32767` for positive). `SherpaSttBackend.transcribe()` converts the segment's `Float32Array` to a plain `number[]` once per utterance (not per frame) before calling `engine.transcribeSamples(samples, 16000)`.

### VAD/segmentation feeding STT
Covered in Section F. In short: `EnergyVad` scores frames, `SentenceSegmenter` accumulates and flushes complete utterances; `minSpeechMs=220`, `endOfSpeechSilenceMs` user-selectable (600/750/1000, default 750), `minVoicedRatio=0.35`.

### Post-processing (both run unconditionally on every STT result, not just for Dolphin/Whisper)
1. `repairScript()` — corrects cross-script Indic output via ISCII-aligned code-point shifting; rejects text that's >40% in an unrelated (non-Indic, non-Latin) script.
2. `isNonSpeechArtifact()` — called in `useTransmitterController.handleSegment`, drops subtitle-artifact phrases and repeated-token loops before a packet is ever built.

### Error handling
- Missing model → `SttEngineProvider.prepare()` catches, remembers the language as unsupported, falls back to simulated, logs loudly (`console.warn`).
- Runtime decode failure → same fallback path, mid-utterance, so one bad decode doesn't halt the pipeline.
- A model install invalidates the "unsupported" memory via `SttEngineProvider.reset()`.

### Model lifecycle / threading
- One engine resident at a time per `SherpaSttBackend` instance; switching languages disposes the old engine (`engine.destroy()`, best-effort) and loads the new one.
- `numThreads: 2` for every model (config-declared, not runtime-tuned).
- All STT calls are `async`/awaited from the JS thread; the actual ONNX inference runs in native code off the JS thread inside the TurboModule, but nothing in this repo manages Kotlin-side threading directly — that's owned by `react-native-sherpa-onnx`.

### Where inference actually occurs / native bridge
`react-native-sherpa-onnx/stt`'s `createSTT()` returns a JS-side handle to a native `SherpaOnnxModule` (TurboModule, Kotlin on Android) instance; `engine.transcribeSamples()` crosses the JS↔Native boundary once per utterance and the actual ONNX Runtime graph execution happens in C++ inside that module. **None of this C++/Kotlin code belongs to iTantra** — it lives entirely in `node_modules/react-native-sherpa-onnx`.

### Layer classification
- TypeScript application logic: everything in `src/core/stt/*.ts`, `src/config/models.ts`.
- React Native bridge: the `require('react-native-sherpa-onnx/stt')` calls inside `SherpaSttBackend.ts`.
- Kotlin (third-party): `node_modules/react-native-sherpa-onnx/android/src/main/java/com/sherpaonnx/*.kt` (`SherpaOnnxModule.kt`, `SherpaOnnxSttHelper.kt`, `SherpaOnnxOnlineSttHelper.kt`, `SherpaOnnxAssetHelper.kt`, `SherpaOnnxArchiveHelper.kt`, etc.) — **third-party, MIT-licensed, not ours.**
- JNI/C++/third-party native library: `sherpa-onnx` (k2-fsa) prebuilt binaries under `node_modules/react-native-sherpa-onnx/third_party/sherpa-onnx-prebuilt/`, plus a bundled `ffmpeg` and `libarchive` prebuilt for audio decode / archive extraction — **third-party, not ours.**

## E. TTS ARCHITECTURE

### Interface / engine / manager / queue
- **`TtsEngine`** (`src/core/tts/TtsEngine.ts`): one loaded native voice at a time. `load()` lazily requires `react-native-sherpa-onnx/tts`, disposes any previous voice, calls `createTTS()`. `speak()` calls `native.generateSpeech(text)`, writes the resulting audio to a WAV file via the package's own `saveAudioToFile` (not a hand-rolled encoder — that's reserved for `debugWav.ts`), then plays it with `expo-audio`'s `createAudioPlayer`. Resolves once playback **starts**, not finishes; a `playbackStatusUpdate` listener signals actual completion. `stopPlayback()` pauses without disposing the voice (used for critical interruption — the voice stays loaded for what comes after).
- **`TtsManager`** (`src/core/tts/TtsManager.ts`): the only class the UI/receiver pipeline talks to. Resolves `packet.language` → voice, loads on demand (reuses an already-loaded voice across consecutive same-language messages), drains the queue continuously (`drain()` loop), and is the sole owner of Android audio-focus behavior: `interruptionMode: 'doNotMix'` for CRITICAL, `'duckOthers'` otherwise, via `expo-audio`'s `setAudioModeAsync`. A CRITICAL arrival mid-playback of a non-critical message calls `queue.requeueFront()` on the interrupted request (it is **not lost** — it plays next after any other critical messages), then `engine.stopPlayback()`.
- **`TtsModelManager`** (`src/core/tts/TtsModelManager.ts`): sibling of STT's `ModelManager`, deliberately isolated under a separate directory (`itantra-tts-models`) so the TTS workstream cannot touch STT model state. Branches `install()` on `source.kind`: `'archive'` (Piper, `.tar.bz2` via k2-fsa release, extracted the same way STT archives are) vs. `'files'` (MMS, loose `model.onnx`+`tokens.txt` from a Hugging Face repo, no archive — progress is weighted by file size, not file count, so a completed tiny `tokens.txt` doesn't visually jump the bar).
- **`TtsQueue`** (`src/core/tts/TtsQueue.ts`): two bands (critical/normal), FIFO within each band, dedup by packet id via a `seen` set that is **never cleared** even by `clear()` — a cleared queue must not let an already-delivered packet's duplicate back in.

### Caching / concurrency / lifecycle
One `TtsEngine` (one native voice) resident at a time; consecutive messages in the same language skip a reload (`loadedModelId === model.id` short-circuit). `TtsManager.drain()` is a single sequential loop guarded by a `draining` flag — no concurrent synthesis/playback is attempted. On queue drain, audio focus is explicitly reset (`resetAudioFocus()`, best-effort). Every failure path (missing voice, engine load failure, synthesis failure, playback failure) reports through `TtsPlaybackState.error` rather than throwing — "one bad message cannot take down the receiver pipeline."

### Critical alert behavior (cross-checked against `iTantra Design.md` §9 and `CriticalAlertBanner.tsx`)
CRITICAL messages: jump the queue, interrupt in-flight non-critical playback (which is requeued, not dropped), use `doNotMix` audio focus, and render a full-width pulsing red banner in the Receiver screen with an "cannot be interrupted" label. There is **no acknowledgement action currently implemented** in code — the Design doc's mockup shows an `[ACKNOWLEDGE]` button, but `CriticalAlertBanner.tsx` has no press handler or acknowledge state. This is a **documented UI gap** relative to the design reference, not something to silently invent during migration without confirming intent.

### Native Sherpa integration for TTS
Same shape as STT: `react-native-sherpa-onnx/tts`'s `createTTS()`/`generateSpeech()`/`saveAudioToFile()` are third-party TurboModule calls; the underlying Kotlin (`SherpaOnnxTtsHelper.kt`) and C++ ONNX Runtime execution are not part of this project.

**Per the task brief: this TTS implementation is considered validated and must be preserved during migration** — the queue-ordering rules, the audio-focus mapping, and the "never drop a message, always surface an error" behavior are the parts that must carry over exactly; the file-round-trip-then-play mechanism (WAV to disk, then `expo-audio` playback) is an RN-imposed detail that Kotlin can legitimately improve (e.g. feeding PCM directly to `AudioTrack`) without changing observable behavior.

## F. AUDIO/VAD/SEGMENTATION ARCHITECTURE

### Audio capture
- **API used:** `expo-audio`'s `useAudioStream({ sampleRate: 16000, channels: 1, encoding: 'int16', onBuffer })`. Not Android's `AudioRecord` directly — that's several layers below what this project's JS ever touches.
- **Sample rate / channels / format:** requested 16 kHz mono int16; the hardware is not guaranteed to honor 16 kHz (`AudioCaptureService` resamples if it doesn't) — confirmed on the test device (Realme RMX3771) that it does deliver exactly 16 kHz mono, per README/TRANSMITTER.md.
- **Buffer sizes:** OS delivers ~100 ms per callback (~1600 samples); re-chopped into exact 512-sample (32 ms) frames by `AudioCaptureService`, carrying any remainder to the next callback.
- **Threading:** all capture callbacks execute on the JS thread (RN bridge/TurboModule delivers already-marshalled buffers); there is no explicit worker/background thread management in this repo — that's inside `expo-audio`'s native implementation.
- **Permissions:** `RECORD_AUDIO` requested via `requestRecordingPermissionsAsync()` on first `startPtt()`, cached in `micGrantedRef` afterward.
- **Audio focus (capture):** `setAudioModeAsync({ allowsRecording: true, playsInSilentMode: true })` set once, on first successful permission grant.
- **Interruption handling:** if `stream.start()` throws (most commonly another app — an in-progress call — holds exclusive mic access on Android), the controller does **not** silently fall back to synthetic audio; it reports a specific, user-facing error ("Microphone unavailable — another app is using it..."). This was an explicit fix for a documented bug (Problem 7 in `WHAT_WE_DID.txt`).
- **Lifecycle / teardown ordering:** on unmount or `stopPtt()`, the documented-critical order is: stop feeding the pipeline (`activeRef.current = false`) → halt the native stream (`stream.stop()`) → only then release native decoders (`vad.dispose()`, `stt.dispose()`). Reversing this order previously caused a native `SIGSEGV` on the audio callback thread ("pthread_mutex_lock called on a destroyed mutex") — a genuine use-after-free that Fast Refresh's edit-reload cycle was triggering routinely. **This ordering constraint must be preserved in the Kotlin rewrite regardless of what audio API replaces `expo-audio`.**
- **Background behavior:** no explicit foreground-service-driven background recording is implemented in the transmitter path in TS (though the manifest declares `FOREGROUND_SERVICE_MICROPHONE`, presumably for `expo-audio`'s own needs); the TTS/receiver side does have a media-session foreground service (`expo.modules.audio.service.AudioControlsService`) declared in the generated manifest, for background playback controls.

### Audio output
`expo-audio`'s `createAudioPlayer({ uri })` + `.play()`, listening for `playbackStatusUpdate`'s `didJustFinish`. No direct `AudioTrack` usage in this repo.

### VAD
Covered in detail in Section D/C. Summary: `EnergyVad` (adaptive noise floor + ZCR) is the only backend actually driving the segmenter today; `SileroVad` exists as an opt-in alternative requiring manual setup and is unused by default (`react-native-sherpa-onnx@0.4.3`'s bundled VAD subpath is a documented no-op that always throws, which is *why* `SileroVad.ts` exists as a workaround via a separate `onnxruntime-react-native` peer dependency).

### Sentence segmentation
`SentenceSegmenter` state machine — see Section C for the file's own documented behavior. Numeric parameters that must carry over exactly for parity:
- `frameSize = 512` (32 ms @ 16 kHz)
- `speechThreshold = 0.5`, `silenceThreshold = 0.35` (hysteresis band)
- `endOfSpeechSilenceMs`: user-selectable 600/750/1000, default **750**
- `minSpeechMs = 220` (below this, discarded as click/cough)
- `maxSpeechMs = 15000` (hard cap, forces a flush)
- `preSpeechPaddingMs = 240` (pre-trigger ring buffer, prevents onset-consonant clipping)
- `MIN_VOICED_RATIO = 0.35` (a segment less than 35% "voiced" by frame count is dropped rather than decoded)

We were explicitly instructed not to change any of these values, and none were changed in this audit — they should be transcribed verbatim into the Kotlin `VadConfig`/`SentenceSegmenter` equivalents.

### What must be rewritten vs. what can be reused
- **Must be rewritten (RN-specific):** `expo-audio` capture/playback calls, the RN bridge glue in `SherpaSttBackend`/`TtsEngine`, `SyntheticAudioSource` (not needed at all — a native app always has a real mic).
- **Can be reused conceptually, ported near-verbatim (pure logic, no RN dependency):** `pcm.ts` math, `EnergyVad`, `SentenceSegmenter`, `indicScript.ts`, `hallucinations.ts`, `priority.ts`, `packetFactory.ts`, `TtsQueue.ts`.
- **Can potentially be reused as actual native code, not just logic:** the sherpa-onnx C++/ONNX Runtime binaries and (with more effort) the third-party wrapper's Kotlin helper classes — see Section I.

## G. PACKET + TRANSPORT ARCHITECTURE

### Packet schema (verified directly against `src/core/types.ts` and `packetFactory.ts` — not assumed from README)

```typescript
export type PacketPriority = 'NORMAL' | 'MEDIUM' | 'HIGH' | 'CRITICAL';

export interface iTantraPacket {
  id: string;             // UUID v4, via expo-crypto's Crypto.randomUUID()
  senderId: string;       // per-install fingerprint (Android ID or random UUID), NOT a peer address
  timestamp: number;      // Date.now(), epoch ms
  language: string;       // BCP-47-ish code, e.g. 'en-IN' — matches config/languages.ts codes exactly
  text: string;           // final, post-repair, post-hallucination-filter transcript
  priority: PacketPriority;   // classifyPriority(text) unless explicitly overridden
  isCompressed: boolean;  // always false today — no compression code exists anywhere
}
```

This matches the README's documented schema exactly — no discrepancy found between documentation and code for this struct.

### Creation / serialization / priority / validation
- **Creation:** `buildPacket()` in `packetFactory.ts` — a pure function, no side effects beyond `Crypto.randomUUID()` and `Date.now()`.
- **Serialization:** **none exists.** The packet is a plain JS object passed by reference from transmitter to `Transport.sendPacket()`; `MockTransport` hands the exact same object reference to receive listeners. There is no JSON encoding/decoding, no binary wire format, no compression — `isCompressed` is a declared-but-unimplemented field ("a declaration about the payload, not a request," per the source comment).
- **Priority detection:** `classifyPriority()` in `priority.ts` — pure keyword substring match against lowercased text, checked in order CRITICAL→HIGH→MEDIUM, first match wins, default NORMAL. Deliberately not ML-based, for auditability.
- **Validation:** **none exists.** No schema validation, no bounds checking on `text` length, no sanitization beyond what `repairScript`/`isNonSpeechArtifact` already did upstream of packet construction.
- **Transmission:** `Transport.sendPacket(packet): Promise<boolean>`.
- **Receiving:** `Transport.onPacketReceived(listener): unsubscribe`.
- **State updates:** entirely within `useReceiverController` — new packet → `ReceivedMessage{state:'received'}` → immediately `'queued'` once handed to `TtsManager` → `'speaking'`/`'error'` driven by `TtsManager`'s state subscription → `'spoken'` once no longer the active TTS request.

### Kotlin equivalent architecture
- `data class iTantraPacket(...)` — direct port, `kotlinx.serialization` or manual JSON if/when a real wire format is added (not present today, so nothing to port for serialization specifically — this is new work).
- `object PacketFactory { fun build(...): iTantraPacket }` and `object PriorityClassifier { fun classify(text: String): PacketPriority }` — direct ports.
- `interface Transport { suspend fun sendPacket(packet: iTantraPacket): Boolean; fun isConnected(): Boolean; ... }` using Kotlin `Flow`/`StateFlow` in place of the JS listener-set pattern.

## H. TRANSPORT AUDIT

**This is the single most important finding of this audit: there is no working phone-to-phone transport of any kind.**

- **`Transport` interface** (`src/core/transport/Transport.ts`): `sendPacket`, `isConnected`, `onConnectionChange`, `onPacketReceived`. Clean seam, well-designed for swapping.
- **`MockTransport`** (`src/core/transport/MockTransport.ts`): the **only** implementation in the entire repository. It simulates:
  - Send latency (60–150 ms random delay).
  - Configurable failure rate (defaults to 0 — always succeeds unless constructed otherwise).
  - **A loopback**: every successfully "sent" packet is, 120–300 ms later, handed directly to the same `MockTransport` instance's own `onPacketReceived` listeners — i.e., a phone transmitting to itself. There is no second device, no network call, no serialization across a wire, anywhere in this behavior.
  - Test-only escape hatches: `simulateReceive()` (inject a packet as if from a peer) and `setConnected()` (flip the link state for UI testing).
- **Bluetooth/BLE/Wi-Fi/Nearby Connections/WebRTC/sockets/LoRa:** grepped and read across the entire `src/` tree — **none exists.** No native module for any of these is imported, declared as a dependency in `package.json`, or referenced anywhere in TypeScript.
- **The project's own documentation is honest about this** — README calls `MockTransport` "an in-app loopback interface for testing"; `WHAT_WE_DID.txt` states plainly: "THE TRANSPORT IS STILL A LOOPBACK... Real radio or Bluetooth is a separate piece of work."

**WHAT CURRENTLY WORKS:** the full pipeline from mic → STT → packet → (loopback) → TTS → speaker, provably, on a single device, because both controllers share one `MockTransport` instance in `App.tsx`.
**WHAT IS MOCKED:** the entire notion of "sending to another device." Connection state, "packets sent/received" counts, and delivery success/failure are all simulated randomness, not link-layer truth.
**WHAT DOES NOT EXIST:** any radio, Bluetooth, Wi-Fi Direct, mesh, or socket code; peer discovery; peer addressing (packets carry a `senderId` fingerprint, not a routable device identity); acknowledgement/retry semantics beyond the mock's random failure.

### Kotlin transport abstraction recommendation
Keep the same shape — a small `interface Transport` with suspend functions and `Flow`s for connection/packet events — and ship a `LoopbackTransport` (direct Kotlin port of `MockTransport`) as the default, so the rest of the app is provably exercisable exactly as it is today, immediately after migration, with zero behavior change. A real transport (most plausibly Android Nearby Connections API, or BLE GATT for a mesh, or a serial/UART bridge to a LoRa module) is then new work implementing that same interface — this was already the intended extension point in the TS code and should remain one in Kotlin.

## I. NATIVE / SHERPA-ONNX ARCHITECTURE

### Package identity
`react-native-sherpa-onnx@0.4.3` — third-party npm package, author XDcobra, MIT license, repository `github.com/XDcobra/react-native-sherpa-onnx`. Declared in `package.json` as a direct dependency of iTantra. It is a **TurboModule** (per its own `create-react-native-library` metadata: `"type": "turbo-module", "languages": "kotlin-objc"`), codegen name `SherpaOnnxSpec`, Java package `com.sherpaonnx`.

### Layer breakdown (verified by listing `node_modules/react-native-sherpa-onnx/`)
1. **JS/TS API surface** (`src/*`, published as `lib/module/*` + `lib/typescript/*`) — subpaths `./stt`, `./tts`, `./vad`, `./alignment`, `./diarization`, `./enhancement`, `./separation`, `./download`, `./extraction`, `./audio`. iTantra imports only `/stt`, `/tts`, `/download`, `/extraction` (lazily, via `require()`, never a static import — this is deliberate so the app still bundles on web/Expo Go where the native module can't resolve).
2. **React Native TurboModule bridge** — the codegen spec (`SherpaOnnxSpec`) and its generated JNI glue (visible as `SherpaOnnxSpec_autolinked_build` in the app's own `.cxx` CMake tree).
3. **Kotlin layer** (`android/src/main/java/com/sherpaonnx/*.kt`): `SherpaOnnxModule.kt` (the TurboModule entry point), `SherpaOnnxPackage.kt` (RN package registration), and helper classes — `SherpaOnnxSttHelper.kt`, `SherpaOnnxOnlineSttHelper.kt`, `SherpaOnnxTtsHelper.kt`, `SherpaOnnxArchiveHelper.kt`, `SherpaOnnxAssetHelper.kt`, `SherpaOnnxAlignmentHelper.kt`, `SherpaOnnxEnhancementHelper.kt`, `SherpaOnnxExtractionNotificationHelper.kt`, `SherpaOnnxPcmCapture.kt`, `SherpaOnnxTextSegmenter.kt`. This is where model loading, archive extraction (via bundled `libarchive`), and inference calls into the C++ layer actually happen from the Android side.
4. **JNI/C++** (`android/src/main/cpp/`) — the CMake build glueing Kotlin to the prebuilt native libraries.
5. **Prebuilt native binaries** (`third_party/sherpa-onnx-prebuilt/`, `third_party/ffmpeg_prebuilt/`, `third_party/libarchive_prebuilt/`) — the actual `sherpa-onnx` (k2-fsa) C++ / ONNX Runtime engine, plus `ffmpeg` (likely for audio format decode) and `libarchive` (for `.tar.bz2` extraction). Version pinned via `ANDROID_RELEASE_TAG`/`IOS_RELEASE_TAG` marker files, not vendored source.

### Ownership classification (per the audit's explicit requirement)
1. **Our project:** none of the above five layers. iTantra's own code stops at the `require('react-native-sherpa-onnx/stt')` call site in `SherpaSttBackend.ts`/`TtsEngine.ts`.
2. **Third-party dependency:** all five layers above, in their entirety.
3. **Generated/build artifacts:** the `.cxx` CMake trees under `android/app/.cxx/Debug/.../SherpaOnnxSpec_autolinked_build/` in **iTantra's own** (gitignored) `android/` folder — these are RN's codegen output for wiring the TurboModule spec into the app build, regenerated every prebuild, and not meaningful to inspect as source.

### What can be reused in the Kotlin app
Two realistic paths, in order of recommended preference:
1. **Depend on `sherpa-onnx`'s own officially published Android artifacts directly** (k2-fsa publishes AARs/JNI libs independent of any RN wrapper) and write a thin Kotlin `SttEngine`/`TtsEngine` against that API surface directly — no RN, no TurboModule codegen, no bridge overhead at all. This is almost certainly the right call: `react-native-sherpa-onnx` exists specifically to bridge sherpa-onnx into RN; once RN is gone, the bridge has no reason to exist.
2. **Lift the wrapper's Kotlin helper classes** (`SherpaOnnxSttHelper.kt`, `SherpaOnnxTtsHelper.kt`, `SherpaOnnxArchiveHelper.kt`, etc.) as a starting reference for how model loading, archive extraction, and inference calls are wired on Android — useful as documentation/scaffolding even where the code isn't reused verbatim, since it already solves the exact "load an int8 ONNX model with `numThreads`, decode PCM float samples, get text back" problem this project needs.

Either path **does not require rewriting sherpa-onnx's own C++**, satisfying the "retain the proven native inference stack" goal. What gets rewritten is only the *glue* between "app code" and "sherpa-onnx's public API," which shrinks from (TS → RN bridge → Kotlin TurboModule → JNI → C++) down to (Kotlin → JNI → C++) — the RN bridge hop is what disappears.

## L. MEMORY/PERFORMANCE ANALYSIS

Based on the actual code (not measured — no profiling was run as part of this audit; all statements here are architectural, not empirical claims about MB/CPU%):

- **Framework/runtime overhead (React Native + Hermes + Fabric/TurboModules + JS↔Native bridge marshalling):** this is the layer a Kotlin migration removes entirely. It's real overhead (JS engine footprint, bridge serialization for every native call, React's reconciliation for the UI tree) but it is not where this app's heavy lifting happens.
- **STT/TTS models resident in memory:** governed entirely by `numThreads: 2` and whichever model is currently loaded — an IndicConformer model (~188 MB on disk) and a TTS voice (64–114 MB on disk) loaded concurrently is the realistic peak, and that is **native C++ ONNX Runtime memory**, identical in a Kotlin app using the same underlying engine. Migration does not change this.
- **ONNX Runtime graph execution / native libraries (sherpa-onnx, ffmpeg, libarchive):** already 100% native code today, running off the JS thread. **Migration cannot speed this up** — it's the same C++ either way.
- **Audio buffers:** small and constant regardless of framework — 512-sample Float32 frames, a handful of segment buffers capped at 15 s of audio (`maxSpeechMs`). Not a meaningful memory concern in either architecture.
- **UI layer:** React Native's view hierarchy (via Fabric) vs. Jetpack Compose's — Compose is generally lighter and avoids the bridge, but this app's UI is already deliberately minimal (two screens, no heavy lists beyond capped-length logs of 40/60 entries), so this is a modest win, not a dramatic one.

**What migration can realistically improve:** app cold-start time (no Hermes/Metro/RN init), steady-state memory floor (no JS engine + bridge resident alongside the native inference engine), audio pipeline latency/jitter (direct `AudioRecord` control vs. going through `expo-audio`'s abstraction and the bridge), and long-term maintainability/build complexity (no Expo prebuild/autolinking layer to fight with, as evidenced by this project's own `.cxx` CMake trees for half a dozen autolinked codegen specs).

**What migration cannot improve:** STT/TTS decode latency (already native), the fundamental download size of the language models (188 MB IndicConformer / 64–114 MB TTS voices are what they are regardless of app framework), or anything about the mocked transport (that's a missing feature, not a performance characteristic).

## O. MIGRATION PHASES

The codebase's actual dependency shape (audio→VAD→segmentation→STT→packet→transport, independently of TTS/receiver, independently of UI) supports the phase order proposed in the task brief essentially unchanged; the one adjustment worth making is putting the transport/loopback decision early, since both pipelines depend on having *something* to send packets through, and the mock is trivial to build first.

- **Phase 0 — Freeze RN baseline.** Tag or branch the current working RN app as a reference. Do not delete it until Kotlin parity is demonstrated.
- **Phase 1 — Native Kotlin project skeleton.** Empty Compose app, package structure above, no functionality yet.
- **Phase 2 — Native sherpa-onnx integration.** Decide and prove out the reuse strategy from Section I (direct sherpa-onnx AAR vs. adapted wrapper Kotlin) with a throwaway "load a model, transcribe a bundled WAV" smoke test — this is the highest-uncertainty technical step and should be de-risked before building anything on top of it.
- **Phase 3 — Audio.** `AudioRecord` capture + `AudioTrack`/`MediaPlayer` playback, `PcmMath` port, permission handling, the documented teardown-ordering constraint.
- **Phase 4 — VAD/segmentation.** `EnergyVad` + `SentenceSegmenter` ports, with the exact tuned constants; validate against recorded reference clips for behavioral parity before wiring to live mic input.
- **Phase 5 — STT.** `SttBackend`/`SttEngineProvider`/`SttModelManager`/`IndicScriptRepair`/`NonSpeechFilter`, using the Phase 2 integration; validate against the same reference clips the RN app's dev self-test already uses.
- **Phase 6 — Packet layer.** `PacketFactory`/`PriorityClassifier`, trivial once STT lands.
- **Phase 7 — Transport (loopback).** `LoopbackTransport` — a same-device mock, matching `MockTransport`'s behavior, so the receiver side has something to consume immediately.
- **Phase 8 — TTS.** `TtsEngine`/`TtsManager`/`TtsQueue`/`TtsModelManager`, reusing the Phase 2 integration; validate the priority-interrupt and audio-focus behavior specifically, since it's explicitly called out as "validated, must be preserved."
- **Phase 9 — Transmitter/Receiver ViewModels.** Wire Phases 3–8 into `TransmitterViewModel`/`ReceiverViewModel`, replicating the existing hooks' control flow.
- **Phase 10 — Compose UI.** Build the screens/components against the ViewModels; this can start in parallel with Phase 9 against fake/stub ViewModels if team capacity allows.
- **Phase 11 — End-to-end parity check.** Side-by-side comparison against the frozen RN baseline: same test utterances, same languages, same priority classifications, same TTS playback ordering under critical interruption.
- **Phase 12 — Performance testing.** Cold start, memory floor, audio pipeline latency — compare against the RN baseline honestly, including where no improvement is expected (decode latency, per Section L).
- **Phase 13 — Real transport (new work, not a "migration" of anything).** Implement a real `Transport` behind the existing interface. This was never implemented in RN either, so it is new scope, not parity work — call it out explicitly as such when scheduling.
- **Phase 14 — Remove the React Native project.** Only after 11 and 12 both pass.

Each phase above should leave the Kotlin app in a state that at minimum builds and runs the phases completed so far, per the task's "working checkpoint after every major phase" requirement.

## Q. RISKS / THINGS THAT MUST NOT BE BROKEN

1. **The audio-pipeline teardown ordering** (stop feeding → halt native stream → release decoders). Getting this wrong previously caused a native `SIGSEGV`/destroyed-mutex crash. This is an ordering constraint on native resource lifetimes, not an RN-specific concern — it will resurface in Kotlin if `AudioRecord`, the STT engine, and the VAD are torn down in the wrong sequence relative to their still-in-flight callbacks.
2. **The "no fabricated transcript" rule.** `SimulatedSttBackend`'s current behavior (report duration/loudness, state plainly that no decoder is installed) was a deliberate reversal of an earlier, judged-actively-misleading design. Any Kotlin placeholder decoder must preserve this, not regress toward "helpful-looking fake output."
3. **The hallucination/script-repair safety nets must keep running unconditionally.** Even though the *currently selected* models (IndicConformer, NeMo CTC) don't exhibit the specific bugs these were built for (Whisper's byte-BPE truncation, Dolphin's script confusion), the code runs them on every result regardless of which model produced it — removing them "because the current models don't need it" would be an undocumented behavior change, not a cleanup.
4. **The tuned VAD/segmenter constants.** These were arrived at through the documented debugging history in `WHAT_WE_DID.txt` (voiced-ratio gate at 0.35 specifically to reject Whisper's music/silence hallucinations; pre-speech padding specifically to stop onset-consonant clipping). Treat every numeric constant in `vadConfig.ts`/`EnergyVad.ts`/`SentenceSegmenter.ts` as load-bearing, not a default to "improve."
5. **The TTS priority/interrupt/audio-focus behavior**, explicitly called out in the task brief as validated and must-preserve. In particular: a CRITICAL interruption **requeues** the displaced message rather than dropping it, and audio focus must be exclusive (`doNotMix`/non-ducking) for critical and ducking for everything else — getting these two swapped would be silent and easy to miss in casual testing.
6. **The dual-directory model isolation** (`itantra-models` vs. `itantra-tts-models`) — this was a deliberate choice so TTS work can't accidentally corrupt STT model state. Preserve the separation, and preserve the exact directory names if any field/demo tooling (the README's documented ADB sideloading commands) depends on them.
7. **Not over-scoping the UI from the Design doc.** The Design document explicitly describes a fuller app (Home, Devices, History, Settings, bottom nav) than what is built. The task brief is explicit that this must not become a feature checklist. Confirm actual desired scope with the user before Compose screens beyond Transmit/Receive are built.
8. **The single-shared-transport-instance pattern.** Both controllers must observe the same transport instance and must not be torn down when the other screen is active — this was a previously real, previously fixed bug (packets going nowhere when the Receiver screen was unmounted).
9. **Licensing of the MMS TTS voices.** The source comments flag CC-BY-NC-4.0 as "acceptable only because this project's use is non-commercial." Confirm this is still true for the Kotlin app's intended distribution before shipping the same voices.
10. **Do not conflate "the transport works" with "the transport exists."** Any demo, stakeholder communication, or internal documentation written during migration should continue the current codebase's own honesty about `MockTransport`/`LoopbackTransport` being a same-device loopback, not real phone-to-phone communication.
